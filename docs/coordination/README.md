## Контроль исходной базы

Новые ветки создаются от **одного SHA интеграционной ветки**, содержащего этот документ. До начала работы каждый исполнитель записывает в Issue baseline SHA и хэш текущего HEAD. Координатор меняет интеграционную ветку только после завершённого ревью; прямые записи исполнителей в неё запрещены.

## Стандартная процедура каждого задания

1. Прочитать `README.md`, `docs/architecture/README.md`, `docs/roadmap.md`, `docs/quality-gates.md`, `docs/standards/known-limitations.md`, этот документ и свою Issue.
2. До изменений: `docs/plans/<короткое-название>.md` или подробный план в Issue, где указаны границы, риски, тесты, затрагиваемые интерфейсы.
3. Изменять только свою ветку и согласованные файлы. Не force-push, не переносить коммиты других исполнителей, не открывать PR к `main`.
4. Добавлять негативные тесты, где возможны ошибочные связи, наложения, искажение УГО, изменения номиналов или молчаливая потеря данных.
5. Выполнить `ruff check .` и `pytest -q`, затем открыть Draft PR к `integration/stage0-12` и дождаться CI для Python 3.12/3.13, аудита каталога и проверки wheel.
6. Передать координатору: Issue, PR, SHA, перечень файлов/контрактов, результаты CI и что **не** реализовано. Отдельно отметить потенциальное влияние на другие чаты.
7. Не объединять PR самостоятельно. После замечаний — исправить в своей ветке и повторить проверки. Закрытие Issue только после принятия координатором.

## Приёмочные правила

- CI зелёный для актуального HEAD, тесты и Ruff; отслеживать audit: весь текущий каталог (на дату актуализации 21 УГО) остаётся DRAFT, hard errors = 0; число определять динамически, без жёсткой привязки будущих тестов к 21.
- Наименование, геометрия, полярность и номера физ. выводов стабильны, пока нет специально согласованной миграции.
- ГОСТ-соответствие не утверждается автоматически: отдельно нужны нормативный первоисточник, поэлементная геометрическая сверка и ручное одобрение; `approved` без них запрещён.
- Рабочая область `main` и историческая цепочка PR #2–#9 защищаются организационным запретом на изменения, техническая защита веток зависит от настроек GitHub.
- Перед merge координатор сравнивает diff с последним base, проверяет пересечения файлов с другими PR, формирует итоговую проверку.

## Протокол обмена

Гитхабные Issue/PR/комментарии — источник фактов. Чаты не видят мысли и незавершённые изменения друг друга автоматически. Сообщения между чатами передаёт координатор с точными ссылками и SHA. В случае спорных требований нормативный оригинал имеет приоритет; разногласие отмечается как BLOCKED, а не замалчивается.
