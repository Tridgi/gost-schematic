# R41 — About and GitHub Releases updates

Stacked on the verified RC1 8d805c777f831231704d15a8cff5ba4fc0c3a837. No changes to main or RC1. Stage 1 is implemented in source, not yet accepted.

## Stage 1
Help > About and updates: actual native package version, author, MIT text, allowlisted fixed external links, manual stable-release lookup and opt-in startup lookup. Browser preview explicitly disables update checking. The public GitHub API request sends no auth credentials and has a 10-second timeout. Strict stable numeric version comparison rejects malformed tags and never recommends older versions. A 404 is not proof of being up to date (the repo may be private). No installer is downloaded or run by this stage.

## Stage 2 — mandatory signed self-update
Use official Tauri 2 updater (https://v2.tauri.app/plugin/updater/), not arbitrary downloaded EXE execution. Pin a compatible current updater version (including signed-version verification); update Cargo.lock with real Cargo, review dependency diff. Owner generates and retains a permanent signing key offline with the Tauri signer; commit only public key, provision private key and password as protected GitHub environment secrets, never expose them in chat, logs, artifacts or source. No dummy public key or unsigned fallback. Document recovery/rotation. A private repo requires an owner-approved secure distribution endpoint; never embed a PAT.

Configure HTTPS endpoint https://github.com/Tridgi/gost-schematic/releases/latest/download/latest.json and createUpdaterArtifacts for NSIS. Maintain monotonically increasing real app versions and matching stable release tags. Use a protected release workflow with explicit owner approval, exact checked-out SHA and successful installed-Windows acceptance before publishing exact signed installer, signature and latest.json. The existing Actions artifact is not a public release or a signed updater feed. No publishing or release without explicit approval.

Expose version, release notes, check, download progress, cancel where supported, verified install and restart. Opt-in automatic check by default off; never silently restart or install while the project is dirty, save/export is pending or a dialog is active. Reuse existing close guard, require saved project and explicit install confirmation. Keep update download/verification in native updater, not raw JS shell. Reject downgrade, invalid signature, mismatched signed version, wrong platform, corrupt/truncated bytes, untrusted feed, offline/rate limited network. Separate public metadata from signed installation authority. No arbitrary URL/path/executable from WebView.

Acceptance: new installed version A checks signed controlled release B, downloads, verifies, installs, restarts and reports B; saved project reopened unchanged with same SHA and exports. Negative cases for malformed feed, bad signature, mismatched version, old/same version, no release, no network, dirty project and interrupted install. Test light/dark, keyboard focus, 900/1280/1920 and Windows DPI. Actual installed native Windows test and user acceptance required; keep RC1 available until verified. Include actual artifact/log URLs and exact SHA in #125.

Stage 2 remains open until signing key provisioning, release pipeline and end-to-end installation evidence are complete.

## R41.1 release staging and security decisions
Repository visibility confirmed public. No PAT is needed. Pin Tauri CLI 2.12.6 and target updater 2.14.1 (verify lockfile and latest advisories before integration). Configure `requireSignedVersion: true`, `allowDowngrades: false`; never enable insecure transport/TLS overrides. Tauri CVE-2026-95624 and CVE-2026-95625 require that version in the signature itself, not just the HTTPS manifest, is checked. CLI signing must bind the app version (automatic bundler support or explicit signer `--app-version`). See https://v2.tauri.app/release/updater/v2.12.0/ and https://github.com/advisories/GHSA-p8c6-29q6-cqw7.

The native acceptance manifest now includes app_version and target; older manifests deliberately fail the new staging gate. Run `.github/tools/r41_prepare_update.py` only with the exact accepted installer directory, the signature for those bytes, the owner-approved Tauri public key, a new output directory, exact source SHA, stable version and previous stable version. It requires minisign on PATH, verifies the installer against both SHA-256 and actual signature, checks the trusted signed version, verifies staged bytes again, and writes fixed-name assets and latest.json. This does not publish to GitHub. Offline unit tests use mocks for signature success, so signed real-binary acceptance remains mandatory. Never use a test key for production. The user must generate their own permanent key offline and configure protected signing environment; no private key is requested in chat. Before release, require immutable accepted run identity/manifest and verify the tag points to exact accepted source SHA. The current R41 preview remains unsigned; stage 2 install wiring is not complete.


## R41.2 native installation implementation — pending acceptance

The source now integrates Tauri updater 2.14.1 (pinned), an allowlisted Rust update state machine, a ready-token download/verify/install sequence, a progress display, explicit confirmation and a native operation gate shared with open/save/save-as/export/close. No generic updater permissions are granted to WebView. The actual release URL must match the stable version and the fixed schematik-x64 NSIS asset name emitted by the staging tool. Signed-version enforcement and no downgrades are mandatory. The normal preview config contains no updater key: its plugin is not registered, and the UI offers only public release metadata and the GitHub Releases link. This is intentionally fail-closed.

Owner provisioning (do not send any private key/password in chat):
1. On a trusted offline/local developer machine, install the pinned Tauri CLI. Generate the permanent signing key with the official `tauri signer generate` command, store a backed-up encrypted private key and password securely. The public key alone is distributable.
2. Run `python .github/tools/r41_updater_config.py --public-key <public-key-file> --output <new-overlay.json>`. It validates the public minisign key envelope, sets the only HTTPS feed, signed-version requirement, no downgrade, and updater artifact generation. It deliberately does not choose the release version or take a private key.
3. In a separately approved release candidate commit, use matching increasing app version in the source config and package metadata. Build with the overlay (Tauri CLI `--config`) and protected signing secrets. Do not use the test key in production. The release workflow must pass the exact same overlay to the installed Windows acceptance, validate that the installed app reports signed updates enabled and record key fingerprint/config SHA and actual app version. A signed installer must be the identical bytes tested by acceptance. The existing unsigned CI artifact is not eligible.
4. Sign and stage the accepted NSIS, verify actual signature + signed version + hash with `r41_prepare_update.py`, use the exact stable tag and safe asset name, then publish only after owner authorization. Publishing automation/protected environment setup is still outstanding. Do not attach a new executable to an old tag or change an existing accepted artifact.
5. On isolated Windows testing, use disposable test signing identity and a controlled feed/test binary distinct from production. Validate full A→B install/restart, unchanged saved project, and reject dirty/busy project, bad key/signature/version, downgraded metadata, absent feed and offline cases. Current native production configuration only permits the official GitHub endpoint; a separate test-only harness/overlay must isolate any local feed without weakening production. Existing frontend mock tests are not proof of actual update installation.

Remaining hard gates: actual Cargo compile and native test results on this new SHA; real signature test in CI using minisign with ephemeral keys (no test key committed or published); installed signed A→B acceptance; durable production public-key provisioning and protected publication. The repository previously did not track Cargo.lock; record a real resolved lockfile from CI or authorized machine before release. Do not claim production updater works based on mock/browser results. The native operation gate covers native file operations; dirty/saved state is controlled by editor and must be retested with real UI. The downloaded package currently lives in memory; no resume or cancel-in-progress and a post-download size limit only. Verify and improve bounded download and cancellation before public release.
